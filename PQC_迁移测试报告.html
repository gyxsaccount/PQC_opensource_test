3.5 通过 BC 支持 PQC 的具体改造代码

改造点集中在「接入层」和「密码学配置」，业务代码零侵入。以下为实测改造前后对比（JDK 21 / JDK 27 通用，已验证可运行）。

① 注册 BC Provider

改造前 → 改造后
// 改造前: 无任何额外 Provider
import javax.net.ssl.*;

// 改造后: 注册 BC 原语 Provider + BC JSSE Provider
import java.security.*;
import org.bouncycastle.jce.provider.BouncyCastleProvider;
import org.bouncycastle.jsse.provider.BouncyCastleJsseProvider;

Security.addProvider(new BouncyCastleProvider());      // PQC 原语 (ML-KEM/ML-DSA)
Security.addProvider(new BouncyCastleJsseProvider());  // JSSE (TLS)

② 获取 SSLContext 时指定 BCJSSE Provider

改造前 → 改造后
// 改造前
SSLContext ctx = SSLContext.getInstance("TLSv1.3");

// 改造后
SSLContext ctx = SSLContext.getInstance("TLSv1.3", "BCJSSE");
ctx.init(kmf.getKeyManagers(), tmf.getTrustManagers(), new SecureRandom());

③ KeyManager / TrustManager / KeyStore 指定 BC Provider

改造后（需指定 Provider，否则 PQC 密钥无法加载）
KeyStore ks = KeyStore.getInstance("PKCS12", "BC");
ks.load(null, null);
ks.setKeyEntry("server", privKey, password, certs);

KeyManagerFactory kmf = KeyManagerFactory.getInstance("PKIX", "BCJSSE");
kmf.init(ks, password);
TrustManagerFactory tmf = TrustManagerFactory.getInstance("PKIX", "BCJSSE");
tmf.init(trustStore);

④ 启用 PQC 密钥交换组（新增配置，经典代码无此调用）

新增
// 服务端 (SSLServerSocket)
SSLParameters params = srv.getSSLParameters();
params.setProtocols(new String[]{"TLSv1.3"});
params.setNamedGroups(new String[]{"X25519MLKEM768", "X25519"});
srv.setSSLParameters(params);

// 客户端 (SSLSocket)
SSLParameters params = sock.getSSLParameters();
params.setProtocols(new String[]{"TLSv1.3"});
params.setNamedGroups(new String[]{"X25519MLKEM768"});
sock.setSSLParameters(params);

⑤ 证书生成改用 BC（若需要 PQC 签名证书）

改造后（自签名 X.509）
JcaX509v3CertificateBuilder cb = new JcaX509v3CertificateBuilder(
    subject, serial, notBefore, notAfter, subject, kp.getPublic());
X509Certificate cert = new JcaX509CertificateConverter().setProvider("BC")
    .getCertificate(cb.build(new JcaContentSignerBuilder("SHA256withECDSA")
        .setProvider("BC").build(kp.getPrivate())));

3.6 三方案握手代码改造点（高亮）

以下为三方案startHandshake()前后的具体改造代码。绿色 = 新增/替换，红色 = 移除。

路线 A：BC BCTLS 握手改造

BCPqcTlsServer / BCPqcTlsClient — 握手相关改造点
// ① 注册 BC Provider（改造前: 无）
Security.addProvider(new BouncyCastleProvider());
Security.addProvider(new BouncyCastleJsseProvider());

// ② SSLContext 用 BCJSSE 获取（改造前: getInstance("TLSv1.3")）
SSLContext ctx = SSLContext.getInstance("TLSv1.3", "BCJSSE");
ctx.init(kmf.getKeyManagers(), tmf.getTrustManagers(), new SecureRandom());

// ③ KMF / TMF / KeyStore 指定 BC Provider（改造前: 默认 Sun 实现）
KeyStore ks = KeyStore.getInstance("PKCS12", "BC");
KeyManagerFactory kmf = KeyManagerFactory.getInstance("PKIX", "BCJSSE");
TrustManagerFactory tmf = TrustManagerFactory.getInstance("PKIX", "BCJSSE");

// ④ 握手前配置 PQC 混合组（新增调用）
SSLParameters params = srv.getSSLParameters();
params.setProtocols(new String[]{"TLSv1.3"});
params.setNamedGroups(new String[]{pqcGroup, "X25519", "secp256r1"});
srv.setSSLParameters(params);

// ⑤ 握手调用不变（startHandshake / getSession 零改动）
sock.startHandshake();
SSLSession session = sock.getSession();

路线 B：JDK 27 原生握手改造

JdkPqcTlsServer / JdkPqcTlsClient — 握手相关改造点
// ① SSLContext 用默认 SunJSSE（无需 Provider 改造）
SSLContext ctx = SSLContext.getInstance("TLSv1.3");
ctx.init(kmf.getKeyManagers(), null, new SecureRandom());

// ② 服务端握手前配置 PQC 混合组（改造前: 默认无 PQC 组）
SSLParameters params = srv.getSSLParameters();
params.setProtocols(new String[]{"TLSv1.3"});
params.setNamedGroups(new String[]{"X25519MLKEM768", "X25519"});
srv.setSSLParameters(params);

// ③ 客户端握手前配置同一组（改造前: 无）
SSLParameters sslParams = sock.getSSLParameters();
sslParams.setProtocols(new String[]{"TLSv1.3"});
sslParams.setNamedGroups(new String[]{"X25519MLKEM768"});
sock.setSSLParameters(sslParams);

// ④ 证书用 keytool 预生成（keyalg EC / ML-DSA），KMF 用 SunX509
KeyManagerFactory kmf = KeyManagerFactory.getInstance("SunX509");

// ⑤ 握手调用不变（startHandshake / getSession 零改动）
sock.startHandshake();
SSLSession session = sock.getSession();

6. 关键实证：ML-DSA 证书无法通过 JSSE 完成 TLS 握手

三步递进测试

步骤内容结果
①keytool 生成 ML-DSA 证书✅ OK
②SSLContext 加载 ML-DSA 证书✅ OK
③实际 TLS 1.3 握手❌ FAIL

根因

SunJSSE 的 signature_algorithms 扩展列表仅 18 个经典方案，不含任何 PQC 签名：

ecdsa_secp256r1_sha256 · ecdsa_secp384r1_sha384 · ecdsa_secp521r1_sha512
ed25519 · ed448
rsa_pss_rsae_sha256/384/512 · rsa_pss_pss_sha256/384/512
rsa_pkcs1_sha256/384/512 · dsa_sha256 · sha1(3种) 
※ 无 ML-DSA / Dilithium / SLH-DSA / Falcon

10. 结论与建议

核心结论

  • 密钥交换已可迁移 — JDK 27 / BC BCTLS 原生支持 X25519MLKEM768
  • 后量子签名"算法可用、协议不可用" — ML-DSA 原语可用，但 JSSE signature_algorithms 硬编码
  • 自实现可打通签名链路 — 绕开 JSSE 验证成功，断点在集成层而非算法
  • 生产环境仍建议等待标准 — 自实现不兼容标准 TLS 客户端
