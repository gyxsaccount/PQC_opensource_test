改造点（改造前 vs 改造后）

① 显式指定 SunJSSE 提供者构建 SSLContext

改造前
// 未 pin 提供者（多提供者环境会漂移）

    TrustManagerFactory.getInstance("PKIX");
tmf.init(trustStore);

         new SecureRandom());
改造后
public static final String SUN_JSSE = "SunJSSE";
SSLContext ctx =
    SSLContext.getInstance("TLS", SUN_JSSE);
TrustManagerFactory tmf =
    TrustManagerFactory.getInstance("PKIX", SUN_JSSE);
tmf.init(trustStore);
ctx.init(null, tmf.getTrustManagers(),
         new SecureRandom());

变化：增加 SUN_JSSE 显式指定。若同时注册 BouncyCastle，SSLContext.getInstance("TLS") 会优先命中 BCJSSE（提供者顺序），导致"JDK 方案"名不副实。

② 自定义 SSLSocketFactory 注入 PQC 群组（核心改造）

改造前

// 仅 x25519 / P-256（经典 ECDHE）
改造后
// PqcSocketFactory.configure()

// ["X25519MLKEM768","x25519"]

核心差异：setNamedGroups(["X25519MLKEM768","x25519"]) —— 迁移前只发经典群组，迁移后以 PQC 优先、x25519 兜底。

断点分析

5.1 【关键断点】JDK JSSE 不支持 ML-DSA 证书做 TLS 认证
现象：ML-DSA-65 证书服务端握手失败 No available authentication scheme
根因：对 sun.security.ssl.SignatureScheme 反射枚举，JDK 27 TLS 签名方案不含 mldsa44/65/87，无法用 ML-DSA 私钥签名 CertificateVerify
影响：纯 JDK 方案只能用 ECDSA/RSA 证书；PQC 证书必须依赖 BCJSSE
证据：X509Authentication: No X.509 cert selected for EC/EdDSA/RSA
5.2 【断点】未启用 PQC 群组导致无共同群组
服务端仅 X25519MLKEM768 + 客户端仅 x25519 → SSLProtocolException: No common named group。
结论：一端强制纯 PQC 而另一端未配置则直接断连；迁移必须两端协调、以混合群组打底。
5.3 【断点】PQC 混合群组仅支持 TLS 1.3
客户端强制 TLS1.2 → protocol_version。迁移前提是全面启用 TLS 1.3（避免降级）。
5.4 顺带发现：JDK 27 keytool -keyalg ML-DSA-65 可直接生成 ML-DSA 自签名证书。

② BCJSSE SSLContext（服务端/客户端）

改造前

  KeyManagerFactory.getInstance("SunX509");

KeyManagerFactory 用 BCJSSE 的 X.509，TrustManagerFactory 用 BCJSSE 的 PKIX，否则无法加载/校验 ML-DSA 证书。

③【关键】BCJSSE 逐连接注入 PQC 签名方案与群组

改造前
// 只设群组，不设签名方案

// 结果：ML-DSA 证书服务端握手
// 报 "found no selectable cipher suite"
改造后
BCSSLParameters p = bcSocket.getParameters();

p.setProtocols({"TLSv1.3"});

BCJSSE 不读全局 jdk.tls.signatureSchemes 且默认不含 mldsa；必须逐连接 setSignatureSchemes，否则 PQC 证书握手直接失败。

断点分析

5.1 【关键断点】BCJSSE 默认签名方案不含 ML-DSA
现象：ML-DSA 证书服务端 + 客户端未注入签名方案 → TlsFatalAlert: found no selectable cipher suite
根因：SignatureSchemeInfo 虽含 mldsa44/65/87 但默认 isEnabled()=false；ML-DSA 私钥无法签名 → 服务端过滤全部 TLS1.3 套件
修复：双方显式 setSignatureSchemes 后握手成功（实测）。
5.2 【互操作断点】BC 客户端对 JDK 服务端不可显式设置签名方案
BC 客户端显式注入签名方案 → JDK 服务端 No X.509 cert selected for EC（JDK 服务端缺陷路径）。
修复：对 JDK 服务端不设置签名方案（走 BC 默认），实测互通正常。
5.3 【断点】JDK 客户端无法认证 ML-DSA 证书
JDK 客户端（信任 ML-DSA 证书）→ BC ML-DSA 服务端：服务端 found no selectable cipher suite。
结论：PQC 证书端到端要求两端都支持 mldsa；JDK 端需升级 BC 栈。
5.4 【断点】JDK 无纯 ML-KEM 群组
JDK setNamedGroups(["MLKEM768"]) 抛 IllegalArgumentException；仅 X25519MLKEM768 ↔ 仅 MLKEM768 无共同群组。
结论：纯 ML-KEM 是 BC 独有能力，适合收敛阶段。
5.5 顺带发现（工程层）：BCJSSE setSSLParameters 清空默认套件（需回填）；bctls 依赖 bcutil（缺 jar 报 NoClassDefFoundError）。

p.setCipherSuites(ss.getEnabledCipherSuites());
ss.setSSLParameters(p);

群组顺序决定了"优先 PQC、失败回退"的行为——兼容性与量子抗性的统一来源。

断点分析

5.1 【断点】未启用 PQC 群组的传统客户端 ↔ PQC-only 服务端
客户端仅 x25519 + 服务端仅 X25519MLKEM768 → No common named group。
结论：正确姿势是"客户端 PQC 优先 + x25519 回退"，而不是只升级一端就强制收紧。
5.2 复用断点：JDK 无 mldsa TLS 签名方案（PQC 证书依赖 BC）；JDK 无纯 MLKEM；BCJSSE 默认不含 mldsa；BC 客户端对 JDK 服务端不可显式设置签名方案；注册 BC 后 "TLS" 默认选 BCJSSE。详见方案A/B 对应章节。
