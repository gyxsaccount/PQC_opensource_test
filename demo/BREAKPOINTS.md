# 迁移断点分析 (Breakpoint Analysis)

> 本文档解释 demo 检测到的"断点"含义、成因与消除方法。

## 1. SSH 协商断点的本质

SSH 2.0 协议中, **客户端** 发起 `SSH_MSG_KEXINIT`, 携带按优先级排列的
算法 name-list (KEX / hostkey / cipher / MAC 四类); **服务端** 从自己的
name-list 中选择**双方都支持的第一个算法**。规则:

```
协商成功 = 客户端列表中任一算法 ∈ 服务端列表
协商失败 (断点) = 四类中任意一类无交集 → 连接直接失败
```

**一个断点都不允许出现**, 因为 SSH 的 KEX 是"四选一整体"流程,
任何一类无交集都会导致握手失败。

## 2. 四象限兼容性矩阵 (demo 输出)

| 场景 | 客户端 | 服务端 | KEX | 签名 | 密码 | MAC | 结果 |
|---|---|---|---|---|---|---|---|
| C1 | 迁移前 | 迁移前 | ✅ | ✅ | ✅ | ✅ | 正常 |
| **C2** | **迁移前** | **混合(含PQ)** | ⚠️ | ⚠️ | ✅ | ✅ | **看配置** |
| C3 | 混合(含PQ) | 迁移前 | ✅ | ✅ | ✅ | ✅ | 正常(回退) |
| C4 | 混合(含PQ) | 混合(含PQ) | ✅ | ✅ | ✅ | ✅ | 正常(PQ生效) |

### 关键结论
- **C3 安全** — 升级后的 PQ 客户端可连接旧服务端(自动回退到经典算法)。
- **C2 是主要断点风险** — 升级后的服务端若**只**启用 PQ 算法并删除经典算法,
  旧客户端(含未升级 libssh2)将**无法连接** → 迁移断点。
- **消除方法**: 迁移过渡期服务端必须**同时保留**经典 + 混合算法
  (`KexAlgorithms curve25519-sha256,mlkem768x25519-sha256,...`),
  实现"渐进迁移"。

## 3. 本 demo 检测出的具体断点

运行 `compatibility_matrix.ps1` 后, 断点会出现在:

```
[断点] C2: 旧客户端 → 新服务端 → 失败类别: kex, hostkey
```

含义:
- **KEX**: 旧客户端不支持 `mlkem768x25519-sha256` / `sntrup761x25519-sha512`,
  若新服务端删除了 `curve25519-sha256` 等经典 KEX → 无交集 → 断点。
- **Hostkey**: 同理, 旧客户端不认识 `ssh-ed25519+ml-dsa-44` 混合签名,
  若服务端不再提供纯 `ssh-ed25519` 主机密钥 → 断点。

## 4. 断点消隐策略 (迁移敏捷性)

1. **双轨配置**: 过渡期服务端同时启用经典与混合算法。
2. **混合优先, 经典兜底**: 客户端把 PQ 算法放最前, 经典算法保留在列表尾部。
3. **签名 AND/OR 策略**: 混合签名验证先走 OR(任一通过), 稳定后切 AND。
4. **配额迁移**: 用 `KexAlgorithms` / `HostKeyAlgorithms` 分批次灰度。
5. **监控**: 记录实际协商结果, 无 PQ 连接占比清零后再移除经典算法。

## 5. 断点检测的量化指标

| 指标 | 定义 | 理想值 |
|---|---|---|
| 断点场景数 (breakpoint_scenarios) | 矩阵中握手失败的场景数 | 0 |
| 安全场景数 (safe_scenarios) | 握手成功的场景数 | 4 |
| PQ 覆盖占比 | 成功协商出混合算法的场景数 / 总场景数 | 越高越好 |
| 回退占比 | PQ 客户端被迫使用经典算法的场景数 | 越小越好(过渡期可接受) |
