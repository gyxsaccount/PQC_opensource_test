如何阅读这张表

表头含义 - SSH 握手必须 4 类算法每类都选出一个双方共有的算法:
列含义判定
KEX密钥交换算法: 如何协商出加密密钥matched: <算法> = 协商成功; MISMATCH = 断点
Hostkey主机密钥算法: 如何验证服务器身份同上
Cipher对称加密算法: 传输数据加密同上
MAC完整性校验算法: 防篡改同上
断点4 类中协商失败的类别无 = 握手成功; 列出类别 = 连接失败

核心规则: 任一类别 MISMATCH - 连接直接失败。

场景名含义 (M1/M2 x C1-C4)
  • M1 (软迁移): 新服务端 = 经典 + 后量子同时保留 (渐进式, 不伤旧客户端)
  • M2 (硬迁移): 新服务端 = 只留后量子, 删光经典 (激进, 切断旧客户端)
  • C1: 旧客户端 - 旧服务端 (两个老版本对话)
  • C2: 旧客户端 - 新服务端 (老客户端想连新服务器)
  • C3: 新客户端 - 旧服务端 (新客户端想连老服务器)
  • C4: 新客户端 - 新服务端 (两个新版本对话, PQ 生效)

单元格值: matched: xxx = 协商成功选出该算法; MISMATCH = 无共同算法; 含 mlkem/sntrup = 后量子混合算法 (迁移目标)。

四行关键解读
场景白话解读结论
M1-C2 旧客户端-新服务端(软)老客户端不会 PQ, 服务端退一步用经典算法软迁移下老客户端不受影响 = 向后兼容
M1-C4 新客户端-新服务端(软)双方都会 PQ, 选出 mlkem768x25519-sha256后量子算法真正生效 = 迁移目标达成
M2-C2 旧客户端-新服务端(硬)老客户端只会经典, 服务端只留 PQ, 无交集硬迁移切断所有老客户端 = 最大断点
M2-C3 新客户端-旧服务端KEX 碰巧成功, 但签名只发混合, 老服务端不认严格客户端必须保留经典签名兜底

核心结论: 盯三件事 - 1. 有没有 MISMATCH (有=断点=连不上); 2. M1 全绿 = 渐进迁移安全; 3. M2 有断点 = 必须等客户端全升级。 推荐采用 M1 软迁移; M2 硬迁移只在所有客户端升级完毕后使用。

断点详情

  • C2: 旧客户端 → 新服务端 (pre-PQ→hybrid) - 失败类别: kex, hostkey
  • C3: 新客户端 → 旧服务端 (hybrid→pre-PQ) - 失败类别: hostkey
断点消除策略: 迁移过渡期服务端必须保留经典算法双轨运行, 例: KexAlgorithms mlkem768x25519-sha256,curve25519-sha256,...。

迁移路线图

  1. 阶段 0: 清除弱算法 (上表 20 项), 消灭降级攻击面
  2. 阶段 1: 服务端启用混合 KEX mlkem768x25519-sha256, 保留经典回退 (M1 模式)
  3. 阶段 2: 客户端 (libssh2 + OpenSSL 3.5 + 自实现补丁) 升级, 优先协商 PQ
  4. 阶段 3: 监控无 PQ 连接占比清零后, 再移除经典算法 (M2 严格模式)
